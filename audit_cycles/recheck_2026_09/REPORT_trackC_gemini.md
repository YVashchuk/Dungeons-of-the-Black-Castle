## **Part I: Advanced Accessibility Architecture and Focus Management (WCAG 2.2 AA)**

The transition to WCAG 2.2 introduced nuanced requirements surrounding focus visibility, target geometry, and component occlusion, fundamentally shifting how single-page applications and modal-heavy interfaces must architect their Document Object Model (DOM). The application under review implements a custom accessibility controller (BC\_A11Y\_DIALOGS) that relies on a MutationObserver to monitor .modal-overlay elements1. This centralized approach to dialog management necessitates a rigorous evaluation against the latest compliance metrics.

### **Success Criterion 2.1.2: No Keyboard Trap and the Mechanics of Escape Gating**

Success Criterion 2.1.2 dictates that if keyboard focus can be moved into a component, it must be possible to move focus away using only a standard keyboard interface2. A pervasive misconception within digital accessibility circles is the assumption that the "Escape" key must function as a universal override to dismiss all modal overlays under all circumstances. However, the WAI-ARIA Authoring Practices Guide clarifies that intentional containment—specifically, a programmatic Tab trap—is not classified as a keyboard trap provided a standard, reachable exit mechanism exists within the trapped cycle2. The auditor's mental model must grade the viability of the exit, not the existence of the containment2.  
The application implements a pattern known as "Escape gating," wherein the Escape key is deliberately disabled for highly consequential dialogs—such as combat encounters or luck roll checks—unless an explicit \[onclick\*="closeModal("\] control is physically present within the dialog's DOM1. This architecture is fully compliant with SC 2.1.22. Because the Tab focus remains constrained within the modal, and the user is continuously permitted to navigate toward a programmatic exit (for instance, an action button that advances the game state and subsequently dismisses the modal), the focus is inherently releasable. \[Inference\] It can be inferred that stripping the Escape key functionality during combat forces the user to resolve the game mechanic, preserving state integrity while remaining legally compliant with accessibility standards, as the user is never permanently stranded without a keystroke-based path forward.  
However, the mechanism driving this Tab trap—a MutationObserver attached to the document.body subtree that monitors attribute changes—carries performance implications. \[Inference\] It is highly probable that during intensive combat cycles, where dynamic updates rapidly alter the DOM to reflect fluctuating health points and combat logs, the MutationObserver will trigger numerous redundant evaluations. While this does not violate WCAG guidelines, the processing overhead could introduce micro-stutters on lower-end mobile processors. Optimizing the observer's configuration to exclusively monitor the specific overlay containers, rather than the entire body subtree, would represent a significant mechanical improvement.

### **Success Criteria 2.4.11 and 2.4.12: Focus Not Obscured**

Introduced specifically in the WCAG 2.2 update, SC 2.4.11 (Focus Not Obscured \- Minimum, Level AA) mandates that a component receiving keyboard focus must not be entirely hidden by author-created content, such as sticky headers, floating footers, or non-modal dialogs4. SC 2.4.12 (Focus Not Obscured \- Enhanced, Level AAA) elevates this restriction, requiring that absolutely no fraction of the focused component is obscured6.  
The application utilizes a fixed HUD bar (\#hud-bar) and bottom-anchored mobile sheets (\#overlay-sheet) on viewports measuring 700 pixels or narrower7. When a keyboard or switch-control user traverses the \#c-list choices housed within the .reader wrapper, the browser's native scrolling algorithm attempts to bring the focused element into the visual viewport. However, the browser's default layout engine does not account for position: fixed elements hovering over the document flow. Consequently, the focused choice may be positioned directly beneath the fixed HUD or the bottom sheet, rendering it invisible to the user and resulting in a direct violation of SC 2.4.119.  
The remediation for this occlusion requires the strategic application of the CSS scroll-padding property on the primary scroll container, which in this architecture is the .story-area9. By defining scroll-padding-top and scroll-padding-bottom values that correspond to the physical height of the fixed HUD and the bottom safe-area insets, the browser's scroll-into-view heuristics are mathematically adjusted. The viewport will subsequently halt its scroll before the focused element intersects with the bounding box of the overlay, ensuring clear visibility and compliance with both the Minimum and Enhanced criteria10.

### **Success Criteria 2.4.7 and 2.4.13: Advanced Focus Visibility and Appearance**

The application relies on the :focus-visible pseudo-class to render a highly distinct focus ring, specifically defining outline: 2px solid var(--gold2); outline-offset: 3px; across buttons, inputs, and interactive map controls8. This implementation easily satisfies the foundational SC 2.4.7 (Focus Visible) and ambitiously aligns with the stringent requirements of WCAG 2.2 SC 2.4.13 (Focus Appearance \- Level AAA)12.  
SC 2.4.13 requires that the focus indicator possess an area at least as large as a 2 CSS pixel thick perimeter of the unfocused component, while maintaining a minimum contrast ratio of 3:1 against the surrounding background12. The application's utilization of a solid 2-pixel gold ring separated by a 3-pixel offset guarantees that the indicator boundary is unequivocally discernible, regardless of the underlying component's background hue8. This represents an industry-leading approach to focus management, decoupling the focus aesthetic from pointer-based interactions and heavily prioritizing the visual needs of keyboard navigators.

### **Success Criterion 4.1.3: Status Messages and Cognitive Load**

For assistive technology users, navigating a highly dynamic, text-heavy interface presents the persistent risk of auditory overload. Success Criterion 4.1.3 requires that status messages be programmatically determinable without forcibly receiving focus, allowing screen readers to seamlessly integrate updates into the user's auditory stream15.  
The application strategically employs role="status" and aria-live="polite" on specific item notifications, such as the spell counter chip and luck roll results8. The "polite" designation instructs the screen reader to wait for a natural pause in the user's current activity before announcing the update, preventing the jarring interruption of in-progress speech synthesis16.  
Critically, the documentation notes that the high-frequency combat log and general event log deliberately omit live region attributes, relying instead on manual innerHTML rebuilds1. From an accessibility perspective, this is a highly sophisticated architectural decision. If a rapid-fire combat sequence were wrapped in an aria-live assertive region, the screen reader's buffer would overflow, trapping the user in a backlog of outdated auditory combat telemetry long after the visual state had resolved. \[Inference\] It is evident that the developers prioritized cognitive pacing over absolute parity. To maintain compliance while ensuring users are informed of combat outcomes, the application correctly utilizes a dedicated, persistent screen-reader live region (\#bc-notif-live) for controlled, summarized announcements, shielding the user from the raw verbosity of the granular combat log.

### **Success Criterion 2.5.8: Target Size Optimization versus Human Interface Guidelines**

WCAG 2.2 Level AA introduced SC 2.5.8 (Target Size \- Minimum), which establishes a baseline that the physical size of a target for pointer inputs must be at least 24 by 24 CSS pixels, unless there is sufficient surrounding spacing to accommodate a 24-pixel diameter circle without intersecting adjacent targets17. This criterion was developed to assist users with motor tremors or limited dexterity, mitigating the frustration of accidental misclicks14.  
The application circumvents this minimum entirely by enforcing a global CSS variable, \--tap: 44px, across all interactive elements, including inventory removal icons (.inv-remove), flask consumption buttons (.flask-btn), and map interaction nodes8. This specific measurement is not arbitrary; it is derived directly from Apple's Human Interface Guidelines (HIG), which specify a 44x44 point touch target as the ergonomic baseline required to accommodate the 10-14 millimeter width of the average human finger pad20. By standardizing on 44 CSS pixels, the application vastly exceeds the WCAG 2.2 AA requirement and bridges the gap toward SC 2.5.5 (Target Size \- Enhanced, Level AAA). \[Inference\] The deliberate choice to reset native button appearances (appearance: none; \-webkit-appearance: none;) while injecting a 44-pixel minimum bounding box demonstrates a nuanced understanding of Fitts's Law, directly correlating larger target areas with reduced cognitive and motor friction during high-stakes interaction loops like item consumption or combat strikes8.

## **Part II: Hardware Interfacing, Viewport Geometry, and Rendering Anomalies**

Modern mobile browsers have evolved into complex software ecosystems featuring collapsible toolbars, virtual keyboards, and hardware-level safe areas (notches and home indicators). Integrating a fixed-layer web application into this fluid geometry requires a masterclass in CSS specification adherence and vendor-specific bug mitigation.

### **The Physics of the dvh Unit and Virtual Keyboard Asymmetry**

Historically, web developers relied on the viewport height (vh) unit to size elements to the vertical extent of the screen. However, on mobile devices, 100vh represents the theoretical maximum height of the screen *if* the browser's dynamic toolbars (address bars, tab strips) are hidden23. When these toolbars expand, a 100vh element bleeds outside the visual viewport, truncating crucial interface components23. To rectify this, the CSS Values and Units Module Level 4 introduced the dynamic viewport height (dvh) unit. The dvh metric recalculates its absolute pixel value in real-time as the browser toolbars expand and retract, ensuring the content perfectly fills the genuinely visible area23.  
The application correctly leverages 100dvh for the combat modal (.modal) and the map overlay (.map-modal-shell), theoretically guaranteeing that these critical interfaces remain fully contained on mobile screens7. However, a severe divergence in vendor implementation regarding the on-screen virtual keyboard poses a significant threat to this geometry.  
In Apple's iOS Safari, the deployment of the virtual keyboard physically resizes the visual viewport, prompting the dvh unit to recalculate and shrink the application interface to remain visible above the keys. Conversely, the Google Chromium rendering engine (which powers Chrome for Android) historically isolated the virtual keyboard from the User Agent UI calculations. In Chromium, the deployment of the keyboard does *not* alter the dvh value, meaning the interface remains at its full, uncompressed height, effectively trapping fixed elements—such as a submit button for the riddle input—beneath the impenetrable overlay of the Android keyboard25.  
To resolve this architectural schism, the W3C and Google introduced an opt-in meta directive. Developers must append interactive-widget=resizes-content to the content attribute of the \<meta name="viewport"\> tag25. This specific flag instructs the Chromium rendering pipeline to abandon its legacy behavior and actively resize the dvh metrics in response to keyboard deployment, mirroring the iOS behavior25. Without this fix, the application's reliance on dvh for full-screen modals will catastrophically fail during text input on modern Android hardware.

### **Safe Area Geometry and WebKit's Fixed Positioning Glitches**

The proliferation of bezel-less hardware designs, complete with camera notches and gesture-based home indicators, necessitated the creation of the env(safe-area-inset-\*) CSS functions. These variables allow the browser to dynamically inject padding to prevent web content from being obscured by physical hardware intrusions27.  
The application successfully initializes this geometry by declaring viewport-fit=cover in the meta tag, which commands the browser to push the webpage into the extreme edges of the hardware screen8. Subsequently, the CSS applies padding-top: var(--safe-top) and corresponding bottom insets to the fixed layers (.scr, .modal-overlay, .end-overlay), deliberately stripping the safe-area padding from the body tag7. From a pure specification standpoint, moving the safe-area insets directly onto the fixed overlays is the mathematically flawless approach for a multi-layered application, as it prevents the compounding of padding values across nested containers.  
However, the reality of vendor rendering engines introduces a volatile variable. WebKit, the engine powering iOS Safari, suffers from a documented bug regarding the intersection of env(safe-area-inset-bottom) and position: fixed elements28. On devices running iOS 15 and newer, WebKit attempts to artificially tint the "chin" area (the hardware space surrounding the home indicator) using the background color of the fixed element positioned closest to the bottom of the DOM28. Furthermore, WebKit occasionally fails to calculate the env() values on the initial paint lifecycle, resulting in the values resolving to 0px until the user initiates a scroll event, which forces a repaint and finally applies the correct padding29.  
\[Inference\] Based on the presence of the fixed \#hud-bar and the heavily nested .modal-overlay structures, it can be inferred that users on newer iPhones may experience a visual stutter upon initial load, where the HUD bar rests too low on the screen, intersecting with the home indicator, before abruptly snapping upward upon the first touch gesture. While the CSS is structurally pristine, mitigating this WebKit anomaly often requires the implementation of a micro-polyfill utilizing \-webkit-fill-available or a brief JavaScript timeout to force a layout recalculation immediately following the DOMContentLoaded event30.

### **Scroll Mechanics and the overscroll-behavior Property**

Mobile browsers feature a native "rubber-banding" or "pull-to-refresh" mechanism, providing tactile feedback when a user scrolls past the absolute boundaries of a webpage. For immersive web applications and games, this native elasticity shatters the illusion of a self-contained interface, exposing the underlying browser chrome.  
The application utilizes overscroll-behavior: contain on the \#scr-title container8. The CSS Overscroll Behavior Module allows developers to override the browser's default scroll boundary actions. By specifying contain, the application explicitly instructs the rendering engine to halt scroll chaining. If a user vigorously scrolls the title screen, the momentum is completely arrested at the container's boundary, preventing the parent body or html nodes from rubber-banding8. This ensures the application feels native and rigid. \[Inference\] However, extending this property to the .story-area or the primary .main wrapper would be highly advisable to fully encapsulate the reading experience and permanently disable pull-to-refresh gestures across the entire gameplay loop.

### **Neurological Accessibility: prefers-reduced-motion and the Event Loop**

Animation on the web serves as vital connective tissue, providing spatial context as elements transition between states. However, for users suffering from vestibular motion disorders, sweeping animations and parallax effects can trigger severe nausea and vertigo. The prefers-reduced-motion media query allows applications to detect the user's operating system-level accessibility preferences and gracefully degrade visual motion8.  
The application implements this query with remarkable sophistication. Rather than utilizing the ubiquitous but flawed animation: none or transition: 0s, the codebase defines animation-duration: .01ms \!important;8. This micro-duration is an advanced rendering technique. When animations are set to absolute zero or removed entirely, the browser bypasses the animation lifecycle. Consequently, JavaScript event listeners waiting for the transitionend or animationend events will never fire, permanently freezing the application logic8. By compressing the duration to one-hundredth of a millisecond, the visual motion is entirely imperceptible to the human eye, satisfying the accessibility requirement, while the browser's event loop successfully dispatches the required lifecycle hooks, preserving the integrity of the application's asynchronous logic.

## **Part III: Advanced Typographic Theory and CSS Specifications**

The application's presentation is heavily reliant on orthotypographic precision, defining a complex cascading font stack (Cinzel, Cormorant Garamond, Forum) to differentiate narrative prose, UI chrome, and Cyrillic subsets. The implementation must navigate the arcane rules of the CSS Fonts Module Level 4 and European typesetting traditions.

### **The Physics of Reading and the ch Unit Anomaly**

To optimize the reading flow, the application wraps the primary narrative content within a .reader class restricted by max-width: 72ch8. This architectural decision is rooted in decades of psychophysical research into human reading patterns. The optimal line length for continuous reading is scientifically established between 45 and 75 characters. Lines extending beyond this threshold force the eye to execute excessively long horizontal sweeps. When the eye reaches the end of an overly long line, the "return sweep" to the beginning of the next line becomes cognitively taxing, increasing the probability of "line doubling" (reading the same line twice) or skipping lines entirely.  
However, the reliance on the CSS ch unit to achieve this geometric ideal introduces a profound technical anomaly. In standard parlance, ch implies "character." In the strict definitions of the W3C specification, the ch unit represents exactly one measurement: the advance measure (the horizontal width) of the 0 (zero) glyph in the currently active font7.  
The application utilizes Cormorant Garamond as its primary reading typeface. Classicist serif typefaces frequently employ "tabular" numerals—numbers explicitly designed to share identical widths so they align perfectly in vertical financial columns. If the 0 glyph in Cormorant Garamond is exceptionally wide compared to standard lowercase letters (like a, e, or s), the mathematical reality of a 72ch container diverges wildly from its intent. A container sized to 72 wide tabular zeroes will physically accommodate significantly more than 72 average lowercase characters—often ballooning to 85 or 90 characters per line.  
While the ch unit is flawlessly accurate for monospaced code blocks (where every glyph matches the width of the zero), utilizing it to regulate proportional serif body copy requires empirical visual validation. \[Inference\] It can be inferred that without manually verifying the width of Cormorant Garamond's zero glyph, the 72ch maximum width may be rendering the text columns far wider than the intended 66-75 character optimal band, inadvertently increasing ocular fatigue for desktop users.

### **The CSS Fonts Module Level 4: @font-face Descriptor Violations**

The application defines its self-hosted WOFF2 binaries within fonts.css. However, an examination of the @font-face blocks reveals a critical misunderstanding of modern CSS parsing algorithms. The declarations utilize range syntaxes, such as font-weight: 400 700; and font-weight: 400 600;, explicitly linking these ranges to static font binaries like Cinzel-lat.woff2 and CormorantGaramond-lat.woff231.  
Under the W3C CSS Fonts Module Level 4 specification, declaring a numerical range within the font-weight, font-stretch, or font-style descriptor serves a highly specific programmatic purpose: it explicitly signals to the browser's font matching algorithm that the referenced file is a Variable Font containing the corresponding interpolation axis (in this case, a wght axis)32.  
Variable fonts package the entire design space of a typeface into a single file, allowing the browser to render any fractional weight between the defined boundaries. Traditional static fonts, conversely, contain only the specific weight they were baked with. Because the provided WOFF2 files are static, single-weight binaries, applying a range descriptor constitutes a severe syntax violation that actively disrupts the CSS cascade32.  
When a modern rendering engine encounters a static font file mapped to a range descriptor, it is forced into a state of fallback heuristics. Depending on the specific browser (Blink versus WebKit), the engine may clamp the entire range to the lowest specified value, rendering all text as weight 400, regardless of the CSS applied to the HTML elements32. Worse, if the CSS demands a weight of 700 and the browser fails to locate the correct descriptor, it may attempt to computationally smear the 400-weight glyphs to synthesize a "faux-bold," drastically degrading the typographic quality and altering the font's intended metrics32.  
To rectify this architectural flaw and align with W3C standards, the CSS must be refactored into distinct, individual @font-face blocks for each static weight. The 400-weight binary must be mapped exclusively to font-weight: 400;, and a separate declaration must map the bold binary exclusively to font-weight: 700;.

### **French Orthotypography and the Mechanics of the NNBSP**

The application claims compliance with strict French typographic standards, necessitating precise control over whitespace surrounding punctuation. Unlike English typography, traditional French orthotypography mandates specific spacing rules derived directly from the *Lexique des règles typographiques en usage à l'Imprimerie nationale*34.  
High punctuation marks consisting of two vertical elements—specifically the question mark (?), exclamation mark (\!), and semicolon (;)—must be preceded by an *espace fine insécable* (Narrow No-Break Space, NNBSP, Unicode U+202F)34. The colon (:), due to its historical usage and visual weight, requires a standard *espace insécable* (Non-Breaking Space, NBSP, Unicode U+00A0)35.  
The distinction between a standard space, an NBSP, and an NNBSP is profound within the browser's rendering tree. A standard space is an *espace justifiante*; its physical width dynamically expands and contracts to achieve block text justification36. An NBSP maintains a fixed width (generally matching the standard word space) and prevents the preceding word from breaking onto a new line, stranding the punctuation mark. The NNBSP (U+202F) is a fraction of the width of a standard space—typically one-eighth of an em-quad—creating a tight, visually unified bond between the word and its punctuation while still preventing line breaks36. The documentation indicates that the application's localization engine successfully injects these precise Unicode entities, ensuring the French prose respects the highest echelons of classical typesetting.

### **Ukrainian Cyrillic Extensions and unicode-range Subsetting**

To support Ukrainian localizations, the application introduces the "Forum" typeface explicitly for the Cyrillic subset. Ukrainian orthography requires specific glottal and palatalized glyphs that exist outside the standard Russian alphabet: the Ukrainian IE є (U+0404, lowercase U+0454), the YI ї (U+0407, lowercase U+0457), and the GHE with upturn ґ (U+0490, lowercase U+0491).  
The fonts.css file defines the unicode-range descriptor for Forum as U+0301, U+0400-045F, U+0490-0491, U+04B0-04B1, U+2116;31. The unicode-range property is a powerful optimization tool; it instructs the browser to download and instantiate the font file only if a character within the specified hexadecimal range appears in the HTML document31.  
An analysis of this range confirms that U+0400-045F encompasses the primary Cyrillic block, capturing both standard Russian and the critical Ukrainian є and ї. Furthermore, the explicit inclusion of U+0490-0491 guarantees coverage for the Ukrainian ґ. This precise subsetting ensures that when the browser encounters Ukrainian text, it will successfully trigger the download of the Forum font, seamlessly overriding the Latin-focused Cinzel without invoking computationally expensive fallback algorithms or substituting mismatched generic system fonts.

## **Part IV: Legal Obligations and the SIL Open Font License (OFL) 1.1**

The application relies heavily on open-source typography, utilizing Cinzel, Cormorant Garamond, and Forum, all of which are distributed under the SIL Open Font License (OFL) version 1.131. Understanding the legal boundaries of this license is paramount, particularly concerning distribution models and artifact compilation.

### **The Mechanics of Bundling vs. Selling**

The OFL is a permissive, yet highly specific, copyleft license designed specifically for collaborative typographic projects. The preamble of the OFL 1.1 explicitly states that the licensed fonts may be used, studied, modified, and redistributed freely, under one absolute condition: they cannot be sold *by themselves*37.  
However, Condition 2 of the OFL grants developers the express permission to bundle, embed, redistribute, and even sell the font software when it is integrated into a larger software package or document38. In the context of a commercial video game or web application, bundling the OFL fonts within the application's asset directory is entirely legal, provided the application itself possesses substantial independent value and is not functioning merely as a disguised font distribution vehicle40.

### **Base64 Embedding and the Single-File Paradigm**

The current architecture of the application relies on external .woff2 files housed within a /fonts/ directory, accompanied by a standalone OFL.txt file31. Under the OFL, distributing the fonts alongside a human-readable text file containing the license satisfies the attribution requirements39.  
However, a critical legal vulnerability arises if the application's deployment strategy shifts toward a single-file compiled HTML artifact, where the font binaries are converted into Base64 strings and injected directly into the \<style\> block. In a single-file delivery paradigm, the external filesystem is eliminated, and the standalone OFL.txt file is lost.  
Condition 2 of the OFL 1.1 is unequivocal: *"Original or Modified Versions of the Font Software may be bundled, redistributed and/or sold with any software, provided that each copy contains the above copyright notice and this license"*38.  
The license permits embedding fonts into documents or applications in ways that make extraction difficult (such as Base64 encoding), but it does *not* waive the requirement to preserve the copyright notice and the license text within the distributed artifact39. To maintain legal compliance when compiling a single-file HTML application, the developer must physically inject the entire OFL 1.1 license text, alongside the original copyright notices of the type designers (e.g., "Copyright (c) Denis Masharov"), directly into the artifact. This is standardly achieved by placing the complete text within a standard CSS /\* ... \*/ or HTML \<\!-- ... \--\> comment block immediately preceding the Base64 @font-face declarations41. Failing to embed this text constitutes a direct breach of the distribution terms, technically nullifying the license and rendering the distribution an act of copyright infringement.  
Furthermore, Condition 4 of the OFL strictly prohibits using the names of the copyright holders or the authors to promote or endorse any modified version of the font or the software bundle itself, except to acknowledge their contributions. Similarly, Condition 3 protects "Reserved Font Names" (e.g., "Forum" or "Cinzel"). The developers may use the fonts within the game, but they cannot legally market the game by claiming it features the "Cinzel" font without explicit, written permission from the original designers37.

## **Concluding Synthesis**

The diagnostic evaluation confirms that the application exhibits a highly sophisticated, forward-looking architectural maturity. The integration of cutting-edge CSS paradigms—such as dynamic viewport heights (dvh), complex safe-area insets, and rigorous French and Ukrainian orthotypography—demonstrates a profound commitment to platform-native fluidity. Most notably, the accessibility implementation surrounding WCAG 2.2 AA standards is exceptionally strong. The decoupling of focus aesthetics from pointer interactions, the adherence to 44-pixel touch targets based on human physiology, and the utilization of .01ms animation resets for reduced motion tracking represent an elite caliber of inclusive engineering.  
However, the intersection of modern specifications and legacy vendor rendering engines introduces critical vulnerabilities. The structural violation within the @font-face descriptor ranges must be immediately rectified to comply with CSS Fonts Module Level 4 and ensure typographic fidelity. The viewport meta tag must be augmented to force Chromium to recalculate dvh units during virtual keyboard deployment, safeguarding the interface on Android hardware. Furthermore, the application of scroll-padding is absolutely necessary to resolve the occlusion of focused elements beneath the fixed HUD, satisfying the rigorous demands of SC 2.4.11.  
Finally, the legal boundary defined by the SIL Open Font License must remain a primary consideration during build compilation. Transitioning to a single-file delivery model without embedding the explicit license text transforms an otherwise compliant application into an act of copyright infringement. By addressing these targeted architectural corrections, the application will not merely conform to external web standards, but will stand as a resilient, accessible, and legally impenetrable model of modern web execution.
