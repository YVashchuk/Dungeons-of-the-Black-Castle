## C7 — остаточная кнопка после617

`SMOKE_BRIEF_chatgpt.md:45`: полностью выиграть617, проверить отсутствие ✦ рядом с Продолжить, затем43 без оставшейся кнопки прошлого боя.

**Полная перезагрузка между боями делает вторую половину опыта недоказательной:** DOM новой страницы больше не содержит старых кнопок независимо от качества cleanup. Привычный helper goto(hash)+reload для этого свойства не подходит.

**Найден ближайший новый бой без reload:** после полного завершения617 нажать штатное Продолжить, выбрать1140, затем **1140→17→250**. На1140 выбрать выход17, на17 — «По дороге (250)». Требований к предметам, удаче, плате или магии на этих двух переходах нет; брать партию1140 не нужно. На250 начать новый бой и проверить, что кнопка побега617/165 не появилась.

Это сильная функциональная проверка того же lifecycle, но в отчёте честно назвать **замену контрольного нового боя43 на250**. Точную строку C7 можно пометить «PASS по функциональному эквиваленту;43 после reload не засчитывался» либо разделить на два подусловия; не писать, что непрерывный617→43 выполнен.

**Пути к43:** графический поиск по всемGD choices с учётом `from_section` не нашёл ни одного1140→43 без входа хотя бы в два других боевых параграфа. Даже разрешение всех inventory/spell требований не создаёт безбоевого пути. Поэтому длинный естественный путь не сохраняет смысл «следующий бой после617»: промежуточные старты успеют очистить DOM.

Пример пути с минимумом двух промежуточных боёв (26переходов, не рекомендуется радиC7):

`1140→17→250 [бой]→19→452→205→139→101→933→845→590→915 [бой]→833→1218→1058→899→772→1059→671→42→161→488→359→814→735→1065→43`.

**Hash без reload не поможет в данной сборке:** в`game_logic.js:3280–3288` hash читается только внутри`window.onload`. Обработчика hashchange/popstate, который бы переводил в новый параграф, в`src` не найдено. Изменение адресного фрагмента само по себе не равно смене отображаемого параграфа; нельзя вместо UI вручную вызывать goTo.

## B2 — состояния карточки628

`SMOKE_BRIEF_chatgpt.md:64` назначает`#628`, «Open the fight», и ожидает все четыре состояния: в бою / повержен / ожидает / убежал.

**Несогласованность условий брифа подтверждена кодом:**

- Все враги при старте имеют`fled:false`, `game_logic.js:2469`.
- Единственное присваивание`fled=true` в`game_logic.js` —`:2095`, успешная удача в`promptCanon1175Luck`.
- Эта функция`:2081–2083` требует`cs.special.type==='sec1175'`.
- GD1175 имеет`combat_script:'sec1175_canon_orcs'`.
- GD628 не имеет этого скрипта или проверки удачи; только joins двух орков в4-м раунде / после гибели первого. Следовательно, **состояние «убежал» на628 через законную игру недостижимо**.
- `updateCombatEnemyDisplay:1833` действительно рисует`state-fled`, если такой флаг установлен. Это существует в движке, но неверно назначено одному628 в тесте.

Исправленная матрица:

1. **628, начало:** первый орк в бою, второй/третий ожидают; шкалы HP и их градиент.
2. **628, убийство первого:** первый повержен, остальные активны; не нужно ломать канон ради четвёртого статуса.
3. **1175, первый орк повержен → проверить удачу → успех:** третий «убежал», первый «повержен», второй «в бою». Если удача неуспешна, нельзя объявлять flee проверенным; нужен другой разрешённый свежий опыт либо явная неполнота.

Таким образом, отсутствие«убежал» на628 — **expected-by-data / ошибка сценария B2**, а не баг отрисовки. Вердикт по оформлению четвёртого состояния требует отдельного живого1175.
